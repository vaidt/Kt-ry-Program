The source identities are pinned by full commit and tree SHA, not by a branch name at execution time. The reference inventory workflow fetches only those commit IDs from the public repositories, verifies the checked-out commit, audits each snapshot, and keeps manifest/receipt outputs outside the measured source trees. It performs no source write, build, test, or runtime launch against either target.

The listed commits were the observed `main` tips when this inventory change was prepared on 2026-10-17. A newer upstream `main` does not silently move this pilot; updating either pin requires a separate reviewed change and a new evidence run.

## Evidence generated by the workflow

The artifact is expected to include separate source manifests and audit receipts for RI-PY and RI-RS, a context document binding each target repository ID, commit, tree, manifest and receipt digest to the ASIG workflow run, a SHA-256 checksum list, a signed evidence archive, and the GitHub Artifact Attestation verification output.

The workflow's `PASS` is limited to exact source identity/inventory and authenticated evidence provenance. It explicitly records:

- `runtime_tests_executed = false`;
- `runtime_identity_observed = false`;
- `runtime_qualification_status = BLOCKED`;
- `protocol_conformance_claimed = false`;
- `release_gate_authorized = false`.

## Gates that remain separate

1. **RI-PY runtime:** requires a reviewed, normative/authoritative test selection and explicit source/evidence bindings. The current Core commit message says the CANONICAL-003 implementation change does not ratify DQ-006 closure; DQ6-R4 is a separate governance gate.
2. **RI-RS runtime:** the ASIG adapter captures Cargo/toolchain context but is not a validated binding to the executed machine code. A passing `cargo test` is not currently enough to qualify the Rust runtime as source-identical.
3. **Test completeness:** required test identifiers must be established from an authorized test plan, not invented from whichever test files happen to exist in the repository.
4. **Conformance/release:** no source inventory can authorize implementation changes, ratify specification decisions, certify Aura conformance, or enable a required release gate.

Until those conditions are independently resolved, runtime qualification and release-gate adoption remain **BLOCKED**. The source inventory pilot itself does not change `vaidt/aura-poc-a-core-v3.3`, `vaidt/aura-guard-v1.3`, `vaidt/Aura-Guard`, or `vaidt/aura-specification`.
